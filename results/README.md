# Results

One directory per run, named `<description>-<date>`, holding:

- `environment.json`: both commits and the image digests, runner or node types, kernel, toolchain versions, the storm settings, and the design (blocks, order, pauses); `cluster_kind` (`kind` or `eks`: `--target local` is a kind cluster, and the files say so) and `namespace` (every output carries these with the run id and the start time: the first line of `summary.txt`, the chart footers, each unit's `meta.json` and each storm's report under `qualifiers`; a value a result does not have reads "not recorded", never a guess, and `backfilled` / `adopted.qualifiers_added` list any that were written afterwards); `run_id` (the key that ties the run to its state in the cluster and to every unit's `meta.json` and the charts; `--resume` refuses a directory whose id differs from the recorded run's); `driver_revision` (the commit, `+dirty` if uncommitted); `variants_file` (where the variants file came from and its SHA-256); when the run was stopped and continued, `resumes` (when, by which driver revision, with how many units done), and when units were run again after `bench adopt`, `adopted` (which units, why, and where their earlier files went);
- `variants.toml`: when the run was made with `--variants`, the file as it was, comments included, with the `conf_file`s it names under their relative paths. A record only: the driver reads the parsed variants in `environment.json` and never this copy;
- `raw/`: the load generator's per-burst output for every block. Each storm's `.json` also has `cpu` (the broker and callout pods' CPU use and throttling over the whole storm, read from their cgroups by the driver) and, in each burst, `cgroupCpu` (the generator's own, for that burst); both only for runs made after they were recorded;
- `prometheus/`: only for a run made with monitoring installed (`bench monitoring up`): the second-by-second series that Prometheus kept while it ran, exported when it completed: `storm_cpu_usage_seconds_total`, `storm_cpu_periods_total`, `storm_cpu_throttled_periods_total`, `storm_cpu_throttled_seconds_total` and `storm_cpu_limit_cores`, each `{"resultType": "matrix", "result": [...]}` as Prometheus's range query returns it, one series per container (labels `component`, `pod`, `container`, `node`), and `index.json` saying what was exported. They are counters: a rate is a difference between neighbours, and a counter that falls is a container that restarted. `environment.json` says where the CPU came from (`cpu_source`: `probe`, `exec` or `none`) and the `monitoring` settings;
- `cpu.svg`: drawn from `prometheus/` when it exists: the cores each component used and the share of its scheduling periods it was throttled, second by second, with the bursts shaded. In a burst's own report, `probeCpu` is the probes' reading of the broker and callout across that burst;
- `summary.txt`: the report, regenerated from `raw/` by `uv run bench report`;
- `discarded/<unit>-<time>/`: only when `bench adopt --redo` ran a unit again: the unit's earlier files, set aside and not deleted, so that what was thrown out can still be looked at;
- `queue-<phase>.svg`: for each burst phase, the queue of connections and the share admitted over time, one line per variant (only for runs made with per-connection samples; every run here predates them, including `eks-operator-smoke-2026-11-21`, so none has charts).

Nothing here may contain credentials, hostnames of private systems or personal details. Compare numbers within a run only; absolute numbers from different machines or runs are not comparable.

## What the existing results are

Every directory here was made **before operator mode replaced the earlier authentication** (a password callout, with the accounts written in the broker's configuration and one shared password): `kind-main-vs-lockfree-2026-11-17` on kind, and `eks-smoke-2026-11-18` and `eks-800-1600-2026-11-18` on EKS (Kubernetes 1.34). Their `environment.json` does not name the authentication, because there was only one then. They were produced by the code at git commit `bf93da8` and earlier; the current code cannot reproduce them (check out `bf93da8` to re-run). Numbers from the two authentication setups are not comparable: a connection does different work in each. Runs made from now on record `auth` in `environment.json`.
