# CLAUDE.md: working in nats-connection-storm-benchmark

A framework that storms a broker with synchronized bursts of authenticated connections, for two or more **variants** (a build of nats-server, broker settings, a topology, resources) under identical conditions, and compares them statistically. It reports what it measured, neutrally. Read [README.md](README.md) first (what it measures and what it does not); the files named below say the rest.

**It was built for benchmarking NATS (nats-server in operator mode with an auth callout), but most of it is not about NATS** and could be extended to other systems: the variants and blocked, interleaved design with exact permutation tests (`driver/stormbench/ab.py`, `report.py`), the run state in the cluster and resume (`state.py`, `runcmd.py`), the per-storm Kubernetes Jobs (`kube.py`), the CPU probe (`components/cpuprobe`), the Prometheus deployment (`deploy/monitoring`) and the EKS cluster definition (`eks.py`). What is NATS-specific is the stack (`deploy/stack`: broker, callout), the load generator (`components/loadgen`, which speaks WebSocket and the NATS auth flow), the callout and key provisioning (`components/callout`, `components/provision`), and the broker image build (`images/nats-server`). To benchmark something else, replace those four and keep the rest.

## The record of runs and images, and the pitfalls the runs taught

Three places, by how often they change and how much they cost to read:

- **Pitfalls (below, in this file):** the lessons of past runs that change what you should do. Short, and read every session.
- **[results/INDEX.md](results/INDEX.md): the log, one line per run**, and **`results/<login>/<run>/NOTES.md`: the entry for each run** (the facts from its `environment.json`, which `bench run` writes when the run ends, then three sections a person fills in: *Purpose*, *What it showed*, *What perturbs it*). Open a run's notes only when you need them; do not load them all. **Every run you make gets notes and an index line when it ends, including failed, partial and check-only runs** (say why it was stopped); a test fails if a run directory has no notes, has unwritten sections, or is missing from the index. Do not edit an old entry's numbers: add a dated correction beneath it.
- **[plans/](plans/README.md): runs planned, running or finished, written down before the data exists** (question, hypothesis, prediction, falsifier, design, what needs approval, outcome). Write the plan, with its prediction and falsifier, **before** a run you intend to make, and do not edit them afterwards: add the outcome. A running or finished plan links its run, and a test checks the headings and the links. Plans are not instructions and not approval: ask before the pushes and EKS time they list.
- **[images/PUBLISHED.md](images/PUBLISHED.md): the images pushed to GHCR** with their digests and which are current or retired. Add a row whenever you push; a test fails when a digest pinned in an `eks` overlay or a variants file is missing from it.

Pitfalls from the runs so far (each is in a run's notes):

- **Check where the CPU numbers came from** (`cpu_source` in `environment.json`, `probeCpu` on the bursts) before reading them. A generator image from before the probe ignores `STORM_CPUPROBE`; `eks-monitoring-check` had none and said `probe` anyway. The driver now falls back and says so; `images/PUBLISHED.md` marks which loadgen digests are retired.
- **The callout and the generator throttle.** At 1 CPU the callout was throttled in about 60% of periods during bursts, and the generator in about 35% at 2 CPU; the broker was not. A broker effect is measured through them and can be masked or exaggerated. Read the CPU section of `summary.txt` before crediting a broker change, and say so when reporting. The arithmetic: the callout spends about 0.57 ms of CPU per connection, so at 1 CPU it needs 0.46 core-seconds for an 800-connection burst and 0.90 for 1600, which is 80-82% of the observed 0.56 s and 1.12 s bursts. That is why broker changes move the median auth time but not the time to admit the burst. But the callout is not the only stage near its limit: the broker (1.6 ms per connection, 3 CPU, floor 76%) and the generator (0.83 ms, 2 CPU, 59%) are close behind, and giving the callout three pods (`eks-callout-replicas`) lowered median latency 13% at 800 without shortening the burst there, because the generator then throttled in 47-57% of its periods. Do not say the callout sets the burst length. Nor that the broker's CPU limit paces connection setup (`eks-broker-cpu`): the broker used at most 2.2 cores at 3 CPU and was no faster at 3.5 (its CPU per connection rose 1.61 to 1.85 ms), while halving the limit moved setup only +8% to +24%; a limit below about 2.2 cores costs auth time and burst length instead. The serialized section the profiles found is the better suspect.
- **Speeding up one stage can make a downstream stage's latency worse.** Removing TLS (`eks-notls`) cut setup ~51% and total latency ~27%, but auth latency *rose* 10-25%: with setup faster, connections reached the still-saturated 1 CPU callout more concentrated in time, so it throttled more. Read total latency, not just the stage you changed. Lifting the callout's cap lowered auth 13% but raised the setup before CONNECT (TCP, TLS, WebSocket upgrade) by 13-24%, so total per-connection time did not improve: `bench report` prints the setup/auth split, and setup is two thirds of a connection's time (`plans/broker-cpu-dose-response.md`).
- **Never compare runs from different cluster builds.** The same configuration (`main`, 1600 connections) gave 272 and 279 ms on one cluster and 236 ms on a rebuilt one, and the callout's CPU per connection was 0.57 ms against 0.49 ms: 13 to 15% between builds, far above the +5.2% and -2.7% between two runs on one cluster. Put what you compare in the same run, as variants in the same blocks.
- **A profiled run's timings are perturbed** (block profiling at rate 1), and the mutex-profile images carry a one-line patch. Never compare them with unprofiled runs or unpatched images. Summed lock-wait totals vary a lot between runs: use the shares.
- **Contention is in connection set-up on the server-wide write lock**, not in `accConnsUpdate`'s account lock (under 0.5% of lock wait; `eks-mutex-profile` says who holds it). Do not start from the account lock. But `nolock` (no server read lock in `accConnsUpdate`) is faster than `main` in auth p50 in 7 of 8 runs at 800, and in both 8-block runs by 11-18% at 800 and 13-18% at 1600 (8 of 8 blocks lower each time), by far more than the profile accounts for: its mechanism is not established, and chasing it was dropped on purpose ([plans/nolock-advantage-mechanism.md](plans/nolock-advantage-mechanism.md)): the end-to-end effect is the result, the narrow relaxations are not worth their complexity. Do not call `accConnsUpdate` cheap on the strength of the profile alone.
- **A run with units redone, resumed or backfilled says so in its notes** (`adopted`, `resumes`, `backfilled`); a unit with fewer than all connections admitted is a problem, not a result (`main-b4` in `lock-mux-eks-retry`: a test of mine reached the live cluster).
- **Few blocks mean nothing.** One or two blocks cannot give a p-value that means anything (the smallest possible exact p with 2 v 2 blocks is 0.33). Several comparisons in one run are not corrected for. Report a lead as a lead.
- **The broker's memory does not stay flat under sustained connection churn, good faith or bad.** Two independent runs — `main` (pure good faith, unramped, 64s) and `main_exhaustion` (80% bad-faith, ramped, 24 minutes) — both grew roughly 27 KB of resident memory per *admitted* connection, with no sign of leveling off even after 40 repeated 6000-connection bursts in one broker process (`eks-exhaustion-memory-probe-2026-11-22`). Any run with enough connections (tens of thousands or more, cumulative) will see memory climb for reasons unrelated to whatever that run is actually testing — read a run's own `varz` series (if `--varz` was on) or at least note the broker was not restarted recently before trusting a late-run CPU or latency number as representative of a fresh broker. `plans/held-connection-exhaustion.md` found this while investigating something else; it has not been traced to a cause (no heap profile exists yet — only CPU/block/mutex) and needs its own plan.
- **A stolen ticket signed with the wrong key is not a cheap rejection under auth callout.** Reading plain-nkey `auth.go` suggests the nonce-signature check is the broker's own fast, local, last-step rejection; under this stack's auth callout, that local check still runs and still fails, but the result is discarded and the broker re-delegates to the callout anyway, using a request keyed to a fresh server-generated nkey (not the client's own). A `forged` connection (real ticket, wrong nonce signature) costs ~10s, the broker's full `authorization.timeout`, the same as `incompleteHandshake` — not the sub-50ms a direct source trace of the non-callout path predicts (`plans/bad-faith-storm.md`, `eks-badfaith-sanity-2026-11-22`). Do not reason about auth cost from the plain nkey path when auth callout is configured.

## Commands

Sample startup, run, restart, report and shutdown commands are in [lifecycle.txt](lifecycle.txt). On EKS, `bench cluster up` also creates the TLS Secret and installs the CPU probes and Prometheus (`--no-monitoring` skips it), and `bench run` refuses to start without monitoring installed unless `--no-monitoring` is passed, because a run without it has no per-burst CPU, no Prometheus series and no profiles. Use them as the starting point; `uv run bench --help` and each subcommand's `--help` say the rest. `--dry-run` prints what would run.

## The kinds of deployments

Two **targets**, chosen with `--target` (default `local`), each with its own kubeconfig file so one can never act on the other's cluster:

- **`local`: kind**, on this machine. Images are built locally and loaded (`bench images load-kind`). Kubeconfig `.kube/storm-bench` (or `STORM_KUBECONFIG`). For trying things; its numbers are not the ones to publish.
- **`eks`: Amazon EKS**, created by `bench cluster up --target eks` (eksctl). **Billed by the hour** and `up`/`down`/`infra` need `--yes`. Images are pulled from a registry and pinned by digest in the overlays. Kubeconfig `.kube/storm-bench-eks` (or `STORM_EKS_KUBECONFIG`). Node groups: `brokers` (tainted `dedicated=broker`), `clients` (generator and callout), `infra` (tainted `dedicated=infra`: Prometheus and its EBS volume). AWS needs `AWS_REGION` (no default) and `AWS_PROFILE`.

What runs in the cluster, always in the namespace `storm-bench`:

- **The stack** (`deploy/stack`, Kustomize): the broker (a StatefulSet) and the auth callout (a Deployment whose init container, `provision`, makes the operator and keys). Overlays: `local` and `eks` are one broker; `local-cluster` and `eks-cluster` are three brokers in a cluster. A variant picks its topology with `stack = "<overlay>"`.
- **The load generator** (`deploy/loadgen`): one Kubernetes Job **per storm**, named `loadgen-<label>-<6hex>`, labelled with the run id, unit and attempt.
- **Monitoring** (`deploy/monitoring`, optional, `bench monitoring up`): the `cpuprobe` DaemonSet (one per node) and a one-pod Prometheus StatefulSet with a PersistentVolumeClaim (kind: `standard`; EKS: an EBS `gp3` volume on the infra node).
- **The driver** is not in the cluster: it is `uv run bench` on your machine.

A **variant** is one `[[variant]]` table in a variants file ([docs/variants.example.toml](docs/variants.example.toml), `lock-variants.toml`, `cluster-variants.toml`). A **unit** is one variant's turn in one block (a fresh broker, then the phases: warm, idle, the burst sizes). Blocks run the variants in rotating order.

## How metrics and profiles are harvested and stored

**The rule: anything gathered while a run goes on is harvested by the in-cluster `cpuprobe` and kept in the cluster until the run completes; the driver never harvests live. At the end the driver only exports what the probes and Prometheus kept into the results.** The driver runs on a laptop that may disconnect or restart; collection must not depend on it. Keep this rule when adding a measurement: put the collection in `components/cpuprobe`, serve it on the probe's HTTP API, export it in `runcmd.export_monitoring`.

- **Timings and the queue.** The generator times every connection and writes each storm's report to its Job's log (the Jobs and logs stay until the run completes). The driver copies each into `results/<run>/raw/<unit>-<phase>.json`. Queue depth is derived from the connections' `sentMs`/`doneMs` (client side); there is no broker-side queue metric.
- **CPU and throttling.** The probe reads the cgroup counters (`cpu.stat`, `cpu.max`) of the benchmark's containers at the moment it is asked. The generator asks every probe at the start and end of each burst, so each burst carries `probeCpu` for the broker and callout. Prometheus also scrapes the probe every second onto its PVC; at the end the driver writes the series to `results/<run>/prometheus/` and `cpu.svg` is drawn from them. Without monitoring installed, the driver falls back to reading the cgroups with `kubectl exec` once per storm (`cpu_source` in `environment.json` says which).
- **Broker profiles.** If a variant's `conf_file` sets `prof_port: 6060` and `prof_block_rate: 1` (`profile.conf`), the probe takes the broker's pprof **block** and **mutex** profiles every 2 s and keeps them in its `emptyDir` with their time and pod UID. They are cumulative, so the storms' times (`startedAtMs`/`endedAtMs` in the reports) pick the pair to subtract afterwards. At the end the driver copies them to `results/<run>/raw/profile/` (`index.json` lists them). nats-server never enables the mutex profile: it needs a broker built with `bench images build ... --patch mutex-profile`. `summary.txt` reads them with `go tool pprof`, so `go` must be installed. **A profiled run's timings are perturbed: never compare them with unprofiled runs.**
- **Where it lands.** One directory per run under the runner's GitHub login, `results/<login>/<name>-<date>/` (`GITHUB_USER` or `--github-user`; `bench run` refuses without one, so a repeat of a run by someone else lands beside yours, never over it): `environment.json` (commits, digests, design, qualifiers, `cpu_source`), `variants.toml` (a copy), `raw/`, `prometheus/`, `cpu.svg`, `queue-<phase>.svg`, `summary.txt` (regenerate with `bench report`). Field by field: [results/README.md](results/README.md). Every output says its cluster kind, namespace, run id, start time and who ran it (the GitHub login).

## Run state: one ConfigMap, so the driver can be stopped and restarted

The driver keeps all of a run's state in **one ConfigMap, `storm-run`**, in `storm-bench`: `plan.json` (run id, variants, design, target, namespace, start), `progress.json` (each unit running or done, with its attempt and the broker pod's UID). Which driver owns the run is a Kubernetes `Lease` of the same name (below). Nothing about a run lives only in the driver's memory, so **it can be stopped and restarted without impact**: `bench run --resume` finds the run in the cluster, skips the units that are done, and finishes a unit that was mid-flight from its Jobs' logs when the broker is still the same pod. A unit that cannot be finished is run again from a fresh broker; nothing is mixed. `bench status` shows the run. Details and the failure cases (a killed driver, `--takeover`, `bench adopt`): [deploy/README.md](deploy/README.md), `driver/stormbench/state.py`.

Which driver owns the run is a **Kubernetes `Lease`** (`coordination.k8s.io/v1`), `storm-run` in `storm-bench`, next to the ConfigMap: `spec.holderIdentity` is the driver's token, `spec.renewTime` the last renewal (at every unit and storm), `spec.leaseDurationSeconds` is 300, `spec.leaseTransitions` counts takeovers, and the annotation `storm-bench/pid` names the process. It is **atomic and owned**: it is created with `kubectl create` (which fails if it exists) and changed with `kubectl replace` carrying the `resourceVersion` it was read at (which fails if anyone changed it since), so two drivers starting at once cannot both win; and every renewal reads the Lease first, so a driver that finds another holder has been taken over and **stops** (`LeaseLost`) instead of running beside the new one. The driver needs `get`, `create`, `update` and `delete` on `leases.coordination.k8s.io` in `storm-bench` (cluster-admin has it). Staleness is judged by the reading driver's own clock against `renewTime`; with a 300 s duration ordinary clock skew does not matter, but a machine whose clock is minutes off will misjudge.

If the owning driver was killed (`kill -9`, a crash, a lost laptop), the Lease stays held until it expires: `bench run --resume` refuses, `bench status` shows who holds it and how long ago it last renewed, and **`bench run --resume --takeover`** takes the run over (only when you know the old driver is dead; `--takeover` does not check: if the old driver was alive after all, it loses the Lease at its next renewal and stops). A driver stopped normally (SIGTERM, Ctrl-C) releases the Lease itself and prints the resume hint. `bench run --discard-state` deletes the ConfigMap and the Lease. A run recorded by an older driver kept its lease in a `lease.json` key of the ConfigMap; this driver ignores that key, so finish such a run with the driver that started it or `--discard-state` it.

## Only one run may be active in a cluster at a time

The namespace, the ConfigMap and Lease `storm-run`, the broker, the callout and the storm Jobs are shared and named without a run in them. A second run would replace the first's brokers and delete its Jobs and state. The driver guards against the mistake: it **refuses to start a fresh run while an unfinished one is recorded** in the cluster (it prints the status and the choices), and `--discard-state` throws the old record away but still refuses under a live Lease unless `--takeover` is given. Those flags are for abandoning a run on purpose, not for working around the refusal. **Start a run only when `bench status` shows none in progress (or it is `COMPLETE`).** Do not run two drivers at once, and do not start a new run to "continue" an old one: use `--resume`. Starting a fresh run after a completed one deletes its Jobs and state and clears the probes' profiles, so export what you need (`bench monitoring export <results dir>`) first. Do not change the namespace strategy casually.

## Rules for working here

- **Python:** use `uv` and the project's `.venv` (`uv run ...`, `uv run pytest`); never install into system packages.
- **Never use `~/.kube/config`** or any default context: the driver refuses, and so should you. Tests are guarded by `tests/conftest.py` so a test cannot reach a real cluster; keep it that way (never default an argument to a real backend).
- **Ask before anything that costs money or is outward-facing:** creating or deleting EKS clusters or node groups, applying monitoring on EKS, and pushing images to a registry. State what it costs.
- **Images are pinned by digest** in the `eks` overlays, each with a comment naming its source tag; after changing a component's source, rebuild, push, and re-pin (a test checks the pins exist and name a real component). A patched broker image is never the commit's own tag.
- **Neutral reporting.** Report what was measured, with its caveats (blocks, p-values for several comparisons, profiling perturbation, CPU throttling in the callout or generator). Compare variants within a run only.
- **Tests** (`uv run pytest`; `go test ./...` in `components/cpuprobe`, `components/callout`, `components/provision`; `cargo test` in `components/loadgen`) must pass; docs name commands and paths and a test checks that they exist, so update the docs with the code.
- **Per-run record:** a run ends with its `NOTES.md` written and a line in `results/INDEX.md`; an image push ends with a row in `images/PUBLISHED.md`. Say what perturbed it, and report a lead as a lead.
- **Where things are:** [results/INDEX.md](results/INDEX.md) (the runs), [images/PUBLISHED.md](images/PUBLISHED.md) (the images), [docs/rationale.md](docs/rationale.md) (why separate processes), [docs/operator-mode-plan.md](docs/operator-mode-plan.md) (the auth design), [deploy/README.md](deploy/README.md) (manifests, state, a storm), [images/README.md](images/README.md) (builds, platforms, patches), [infra/eks/README.md](infra/eks/README.md) (the cluster, EBS, costs), [results/README.md](results/README.md), `components/*/README.md`.
