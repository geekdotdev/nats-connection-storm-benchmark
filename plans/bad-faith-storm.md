# bad-faith-storm

**Status:** running. **Run:** [eks-badfaith-sanity-2026-11-22](../results/cfedersp/eks-badfaith-sanity-2026-11-22/NOTES.md) (a sanity check, not yet the full ratio sweep in Design).

## Question

What does a burst of bad-faith connection attempts — invalid, forged, or referencing a non-existent account — cost the broker, and does it degrade a good-faith client sharing the same burst? All prior runs here are a burst of *valid* tickets ("a good faith 1600-strong connection storm"): this plan is the same storm with some or all of the connections carrying credentials built to fail.

## Hypothesis

Four distinct ways a connection can fail authentication, each a different code path in `processClientOrLeafAuthentication` (confirmed by reading `582fb8e939a7`'s `server/auth.go` and `server/client.go`, not assumed):

| Kind | What it is | Where it fails | Cost relative to a real connection |
|---|---|---|---|
| **invalid** | A garbage string where the ticket's JWT goes (not valid base64/JSON, or not a JWT claims structure) | `jwt.DecodeUserClaims(c.opts.JWT)`, **inside** the server lock (`s.mu.Lock()`...`s.mu.Unlock()`), the cheapest and earliest exit | Lowest: one failed decode, no account lookup, no signature check, no callout |
| **nonexistent-account** | A structurally valid, properly-signed JWT whose issuer account public key was never provisioned at all | Decodes fine, unlocks, then `s.LookupAccount(issuer)` itself returns nil (`auth.go` line 1040) | Second-lowest: decode + validate + one failed lookup |
| **forged** | A genuinely real, validly-issued ticket — the same JWT a good-faith connection would use, untouched — but the CONNECT frame's nonce challenge (`sig`) is signed with a throwaway keypair instead of the key matching the ticket's own `sub`: a stolen-ticket-without-the-key attempt, not a forged JWT | Everything else about the ticket passes: decode, claims validation, `LookupAccount`, `hasIssuer`/`ValidateScopedSigner` all succeed; it fails at the very last check, `nkeys.FromPublicKey(juc.Subject).Verify(c.nonce, sig)` (`auth.go` lines 1127-1132), confirmed by tracing the full call chain: `isClientAuthorized` returns false → `checkAuthentication` false → the caller in `processConnect` calls `c.authViolation()` → client gets `-ERR 'Authorization Violation'`, connection closed | **Highest of the four**, by construction: it is the last check in the whole chain, so every cheaper check upstream of it has already run and succeeded. Needs almost no new generator code: `ticket.rs` already builds a valid `Ticket` and already has `sign_nonce`; this kind only swaps in a throwaway keypair at the point the generator signs the nonce |
| **incomplete-handshake** | TCP + TLS + WebSocket upgrade completes, the broker's INFO is received, and the client then sends nothing — no CONNECT frame at all | Nothing on the wire; the broker's own 10 s `authorization { timeout }` (`deploy/stack/base/broker-config.yaml`) fires `c.authTimeout()` and closes it | The only genuinely silent case; holds a goroutine, a TLS session and an open socket for up to 10 s per attempt, not CPU |

Confirmed directly, end to end, for every kind above: every explicit `return false` branch in `processClientOrLeafAuthentication` reaches the same place, the caller in `processConnect` seeing `checkAuthentication` return false, which calls `c.authViolation()` and sends `-ERR 'Authorization Violation'` before closing. The one earlier idea this plan is *not* using: a JWT whose own issuer signature is forged (a fake ticket, not a stolen real one). That is a different, separately-interesting thing to measure later — it needs new JWT-building code in the generator that **forged**, as defined here, does not — and is not part of this run.

**TLS stays on.** This storm uses the deployed `wss://` configuration throughout (no `no_tls`): a bad-faith storm is about what an attacker reaching the real, deployed broker costs, not an isolated crypto question (that was `plans/tls-cost.md`).

## Prediction

Written before any code exists to test it, so these are order-of-magnitude, not point estimates (recorded here to be falsified, not adjusted after the fact).

1. **Per-attempt broker cost, in rejections/CPU-ms, orders from cheapest to priciest:** `incomplete-handshake` (near zero CPU, but holds a slot for ~10 s) < `invalid` < `nonexistent-account` < `forged` < a real connection. **forged** runs every check a real connection does except the callout round trip, so it should be the closest of the four to a real ticket's broker-side auth cost (within a factor of 2, not an order of magnitude cheaper) — closer than any kind that fails before the account lookup.
2. **Good-faith degradation, mixed burst:** at a bad:good ratio up to 1:1, good-faith auth p50 should move less than 20% from a good-faith-only burst of the same total good-faith count (the broker-side rejection paths are short compared to a real connection's work, so a roughly equal volume of bad traffic should not swamp it). Above some ratio (to be found, not assumed), good-faith latency should degrade materially, because the bad-faith traffic still contends for the same server lock (all four kinds pass through parts of the connect path, and three of four take it) and the same accept queue.
3. **incomplete-handshake is the one worth the most caution:** N concurrent attempts per second, sustained, accumulate toward ~10×N held connections at steady state (the 10 s timeout). This is a resource question (file descriptors, memory, TLS session state) more than a CPU one, and is the kind most likely to show a cost this stack's CPU-based measurements so far have not captured.

## Falsifier

- If **forged** does not cost meaningfully more than **nonexistent-account** (the next cheapest kind that still fails before the nonce check), the nonce-signature verification is not where the cost concentrates, or the other checks ahead of it are cheaper than estimated; revise before drawing conclusions from the other kinds.
- If good-faith latency degrades by more than 20% at a 1:1 bad:good ratio, the broker is more sensitive to rejection traffic than predicted, and the "three stages near capacity" picture from the earlier runs needs a fourth: rejection handling.
- If `incomplete-handshake` shows no measurable broker-side cost (CPU, memory, or held sockets) even at high concurrency, the 10 s timeout and whatever backs an unauthenticated connection are cheap enough not to worry about at this scale, and that's worth stating plainly rather than assuming it's a risk.

## Design

**Containment (built, not yet applied to the live cluster):**
- `bench cluster network-policy --target eks --yes` turns on `vpc-cni`'s own `NetworkPolicy` enforcement (off by default on this cluster; a bare `NetworkPolicy` object is otherwise accepted by the API server and enforced by nothing). One-time per cluster, thrown away by `cluster down` like everything else.
- `deploy/loadgen/overlays/eks-restricted` (new, verified against real `kubectl kustomize`): layers one `NetworkPolicy` onto the unchanged `eks` overlay, selecting only the generator's own pod. **Ingress: denied entirely.** **Egress: DNS (kube-system's `kube-dns` only), the broker's `wss` port 8443 only (never the plain `4222`, which this generator never uses), and the CPU probe's `9100` (for monitoring) — nothing else, no public internet.** Used with `--loadgen-overlay deploy/loadgen/overlays/eks-restricted` on the `run` command; the default `eks` overlay every other run uses is untouched.
- GHCR is unaffected on purpose: image pulls happen on the node, outside any pod's network namespace, before the generator's own `NetworkPolicy` (or any pod's) ever applies. No VPC, subnet or NAT change, and nothing above touches any pod but the generator's.
- The broker, callout and probe pods keep their current, unrestricted networking; only the pod capable of producing bad-faith traffic is boxed in.

**What is *not* built yet, and needs its own look before anything runs:** the generator-side code that actually produces the four kinds above. This is new logic that signs and forges credentials (even synthetic ones, inside this isolated stack) and deserves review on its own terms, not folded silently into this plan:
- `components/loadgen/src/ticket.rs` gains a mode building each of the four kinds (the "real" path already exists and is the control group). `forged` needs almost nothing new: a real `Ticket` from the existing `Issuer`, with the nonce signed by a fresh, unrelated keypair instead of `ticket.sign_nonce(nonce)`. `nonexistent-account` reuses the existing JWT-encoding logic, pointed at an account public key that was never provisioned. `incomplete-handshake` is a connection that completes the WebSocket upgrade and then simply never writes a CONNECT frame.
- A generator setting controlling the mix per burst (a bad-faith fraction and a weighting across the four kinds), so a single burst can carry both a good-faith control group and bad-faith traffic side by side, and the report can score the good-faith subset's own latency separately from the bad-faith subset's rejection time and whatever error (if any) each kind actually receives.
- A calibration step, run before the real storm: measure the generator's *own* CPU cost per bad-faith kind (signing a forged JWT is not free client-side either — TLS alone already cost the generator 0.4-0.9 ms per connection in `eks-notls`). **Scale the generator up first** (`generator_resources` CPU, `STORM_THREADS`) so the generator itself is never the limiting stage; if that saturates a client node even after raising both, the next lever is running more than one generator Job in parallel (not supported today — `generator_resources` patches one pod; horizontal scaling would need a new `parallelism`-style variant key), to be added only if the vertical lever actually isn't enough.

**The run itself, once the above is approved and built:** `main`, TLS on, monitoring on (CPU from the probes, as every run since `eks-monitoring-check`); one or more blocks sweeping the bad:good ratio (0%, 25%, 50%, 100%+ bad-faith by connection count) at a fixed good-faith count per burst, with the four bad-faith kinds reported separately. Run on the isolated overlay, never the default one.

## Needs approval

Three separate things, at three separate levels of cost and risk:
1. **`bench cluster network-policy --target eks --yes`** against the live cluster — an infra change (affects every pod's networking), no AWS cost beyond the cluster's own hourly rate, reversible by `cluster down`. Not done.
2. **Writing the generator's bad-faith ticket code** (`components/loadgen/src/ticket.rs` and a new storm mode) — new code, no cluster cost, but it is credential-forging logic and was reviewed on its own, separately from this plan being approved. **Done, 2026-11-22**, built against the exact credential definition in the Design section above (the user clarified `forged` directly: a real ticket, the nonce signed by the wrong key, not a forged JWT issuer): `ticket.rs` gained `Issuer::random` (a self-consistent, never-provisioned account, for `nonexistent-account`) and `sign_nonce_with_unrelated_key` (for `forged`); `main.rs` gained `STORM_INVALID_FRACTION`, `STORM_NONEXISTENT_ACCOUNT_FRACTION`, `STORM_FORGED_FRACTION`, `STORM_INCOMPLETE_HANDSHAKE_FRACTION` (each 0.0 by default, so every existing run's behavior and every existing report's fields are unaffected), a `Kind`/`Credential` pair of types, and a `badFaith` section in the report, present only when something is configured. The burst's own `seconds` and CPU snapshot are taken when the good-faith subset finishes, not when bad-faith stragglers (`incomplete-handshake` can sit for the broker's own ~10 s authorization timeout) do, so "burst length" stays comparable with every run before this existed. 12 new Rust tests (`cargo test`: 38 passing, up from 26), all offline (no broker): the forged signature genuinely fails verification against the real ticket's own key, the rogue account is self-consistent but never collides with the real one, the kind-assignment counts and rounding are exact, and the snapshot-timing decision fires on good faith alone. Not exercised against a real broker (that is step 3, below).
3. **Running the storm on EKS** — ordinary EKS time (~$1.1/h, same cluster), after both of the above. **Done, 2026-11-22**, at the sanity level (one block, 200 connections, the ratio in `bad-faith-variants.toml`'s `main_badfaith`: 60% good-faith, 10% each kind) on the `eks-restricted` `NetworkPolicy` overlay, with `bench cluster network-policy --target eks --yes` turned on first and verified (the `aws-eks-nodeagent` container present in every `aws-node` DaemonSet pod). The full ratio sweep across 8 blocks described in Design has not run; that is a separate decision (more cluster time, and worth revisiting the `forged` finding below first).

## Outcome

**2026-11-22, sanity run** ([eks-badfaith-sanity-2026-11-22](../results/cfedersp/eks-badfaith-sanity-2026-11-22/NOTES.md), full detail there): `invalid` and `nonexistentAccount` confirmed the prediction — fast rejections (p50 18-22ms), cheaper than a good-faith connection's auth time in the same burst.

**`forged` falsified Prediction #1, but in the opposite direction from the stated Falsifier.** The Falsifier asked whether `forged` would fail to cost *more* than `nonexistentAccount`; instead it cost **~500x more** — all 20 attempts took 10020-10047ms to fail, indistinguishable from `incompleteHandshake`'s ~10s broker timeout, not the fast last-check rejection the source trace of plain nkey auth (`auth.go`'s `nkeys.FromPublicKey(juc.Subject).Verify`) predicted. Traced (not assumed) why: under this stack's auth-callout configuration, that local signature check still runs and still fails, but its result is discarded — the broker unconditionally re-delegates to the external callout afterward, using a request keyed to a **fresh, server-generated one-time nkey** (not the client's own, "to prevent replay attacks" per the broker's comment), with the client's real nkey and signature passed through only as unverified metadata. This repo's own callout (`components/callout/operator.go`) never inspects that metadata, so it should accept an untouched, validly-issued `forged` ticket quickly regardless. The error text on the 20 failures (`-ERR 'Authorization Violation'`, the callout-timeout path's own message, not the distinct "Authentication Timeout" string the no-CONNECT timer uses) confirms this *is* the callout round-trip's own `authorization.timeout` expiring, not a different timer that happens to share the same ~10s config value. The one link not pinned to a specific line of code: why an apparently fast, local, non-networked callout accept still leaves the broker's wait unresolved for the full timeout. The callout pod that served this run's traffic was recycled (an unrelated diagnostic restart) before its own accept/reject/drop counters could be read back, and re-running to recapture them was judged not worth the cluster cost for a sanity check — revisit if this plan's full sweep goes ahead, since restarting the callout mid-sweep to read its counters is cheap and the question is worth closing.

**Practical upshot, regardless of the exact last line of code:** a "forged" bad-faith connection — a stolen real ticket signed with the wrong key — is not a cheap rejection under this stack's auth-callout design. It costs the broker a full ~10-second held connection, goroutine, TLS session and socket, the same as `incompleteHandshake`. Prediction #3's caution about `incompleteHandshake` ("the one worth the most caution... a resource question more than a CPU one") now applies equally to `forged`, which doubles the volume of traffic that can hold connections open at near-zero attacker cost (no need to actually complete a handshake or hold a socket client-side waiting — the generator's own `forged` attempts are also cheap to produce, being a real ticket plus one throwaway keypair).

Prediction #2 (good-faith degradation at a mixed ratio) was not cleanly tested in this run — the mixed burst had 120 good-faith of 200 total against `main`'s 200-of-200, a different total count that confounds queueing on its own. No good-faith errors or refusals were seen at 60:40 good:bad, but a real test needs the Design's matched-good-faith-count comparison across ratios, not yet run.

**Next:** decide whether to run the full ratio sweep (worth it now that `forged` is known to be as expensive as `incompleteHandshake`, which changes what the sweep would be measuring — effectively two kinds of "held connection" attack instead of one cheap and one expensive), and whether to spend a bit more cluster time closing the last link in the `forged` mechanism (read the callout's own counters mid-run next time, by scraping its log before the next variant's apply recycles the pod).
