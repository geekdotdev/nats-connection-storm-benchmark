# held-connection-exhaustion

**Status:** dropped (2026-11-22: satisfied with the broker's performance and sound in the findings so far; further benchmarking on this line is paused until there is a reason to scale). **Run:** [eks-exhaustion-calibration-2026-11-22](../results/cfedersp/eks-exhaustion-calibration-2026-11-22/NOTES.md), [eks-exhaustion-memory-probe-2026-11-22](../results/cfedersp/eks-exhaustion-memory-probe-2026-11-22/NOTES.md) (the calibration step and its memory follow-up, size 6000 only — the sweep's other three sizes were never run).

## Question

`forged` and `incompleteHandshake` (the two bad-faith kinds found to cost the broker a full ~10s held connection each, [eks-badfaith-sanity-2026-11-22](../results/cfedersp/eks-badfaith-sanity-2026-11-22/NOTES.md), not the cheap rejection `plans/bad-faith-storm.md` predicted) were only ever tested 20-at-a-time. At what sustained volume of concurrently-held connections, if any, does the broker's own resources (memory, connection handling) start to degrade, and does good-faith traffic sharing the same window suffer for it? `invalid` and `nonexistentAccount` are excluded here: they are confirmed cheap (sub-50ms) and do not hold anything open, so they dilute rather than sharpen this question.

## Hypothesis

Each `forged` or `incompleteHandshake` attempt occupies a broker-side connection (a goroutine, a TLS session, socket buffers, and for `forged` an outstanding `$SYS.REQ.USER.AUTH` wait) for almost exactly the broker's `authorization { timeout: 10s }`. There is **no `max_connections` configured** on this broker (`deploy/stack/base/broker-config.yaml` has none), so nothing in the broker's own config backpressures the number of unauthenticated connections it will hold open at once. At a sustained arrival rate of *R* bad-faith connections/second, the steady-state held count should approach *R* × 10s once the window has run longer than 10s (Prediction #3 of the original plan, never tested past *R* ≈ 2/s, 20 connections fired together).

**The generator cannot create this by repeating bursts.** Traced directly in `components/loadgen/src/main.rs::run_once`: the function's `rx.recv()` loop only finishes once every spawned task — including every `forged`/`incompleteHandshake` straggler, which can each take the full ~10s — has sent its record, and `real_main`'s outer loop (`for i in 0..c.runs`) fully awaits one `run_once` before sleeping `pause_ms` and starting the next. Bursts are strictly sequential; stragglers from burst *N* cannot overlap burst *N*+1. The only existing lever that creates genuine overlap **within** one burst is `STORM_RAMP_MS` (spreads a burst's *own* connection starts evenly over a window, already free to set via a variant's `storm` table, no new code) combined with a large enough burst `size` (`--sizes`, the framework's existing load-sweep dimension). Setting `STORM_RAMP_MS` well past 10s turns one burst into a sustained arrival process instead of a synchronized spike, and sweeping `size` at a fixed ramp and fixed bad-faith fraction scales the arrival rate (and so the predicted steady-state held count) directly.

## Prediction

1. **Steady-state held count tracks arrival rate × 10s**, within a factor of 2, up to whatever point (if any) the broker's own capacity bends the curve. At `STORM_RAMP_MS = 30000` and 80% bad-faith (40% `forged`, 40% `incompleteHandshake`), burst sizes 250 / 1000 / 3000 / 6000 give bad-faith arrival rates of ~6.7 / 26.7 / 80 / 160 per second and predicted steady-state held counts of roughly 67 / 267 / 800 / 1600.
2. **Good-faith connections sharing the window degrade only once held count becomes a large fraction of what the broker can comfortably hold.** At the smallest sizes, good-faith admission and auth latency should look like a plain burst of that good-faith count alone (no refusals, no timeouts). Somewhere in the sweep (not assumed where) this should change — either gradually (latency climbs) or sharply (admissions start failing) — or it should not change at all up to 1600 held, which is itself a useful, reportable result (the broker handles this volume fine at this scale).
3. **Broker memory (`nats-server`'s own `/varz`, read directly — see Needs approval) climbs with held count and stays under its 4Gi cgroup limit at every point in this sweep.** If it approaches the limit before the largest size, that is the more alarming and more important finding than anything in Prediction 2.

## Falsifier

- If held count does **not** scale with arrival rate (e.g. it plateaus well below the `R × 10s` estimate at every size, with no corresponding good-faith degradation or broker error), something is capping concurrency before the broker's memory or connection handling is ever actually tested — most likely the generator pod itself (see calibration in Design) rather than the broker. Say so plainly rather than reporting a null result as "the broker is fine."
- If `forged`'s or `incompleteHandshake`'s own authMs/error timing drifts well past ~10s as held count grows (rather than staying flat near the configured timeout), the broker's accept loop or timer handling is itself degrading under load — a more specific and more interesting finding than generic "it got slower."
- If good-faith latency degrades sharply at a size where predicted held count is still a small fraction of 1600, Prediction 1's scaling estimate is in the right ballpark but Prediction 2's "only once held count is large" assumption is wrong — revise before extrapolating further.

## Design

**Reuses the existing framework; no new generator code for the core sweep.** One new variant (or two: `main` as an unchanged control, `main_exhaustion` carrying the fractions and ramp below), in a new `exhaustion-variants.toml`:
- `STORM_FORGED_FRACTION = "0.4"`, `STORM_INCOMPLETE_HANDSHAKE_FRACTION = "0.4"` (80% bad-faith, split evenly between the two held kinds; `invalid` and `nonexistentAccount` left at 0, per the Question above).
- `STORM_RAMP_MS = "30000"`: spreads each burst's connections over 30s, long enough past the ~10s hold that the back two-thirds of the window should show genuine steady state, not just a transient pile-up from one synchronized spike.
- `--sizes 250,1000,3000,6000` (or close to it) on the existing `--sizes` CLI flag — the only lever that changes arrival rate here, since fractions and ramp are fixed across the sweep. Good-faith counts at these sizes are 50 / 200 / 600 / 1200: small but workable for reading good-faith outcomes/latency at each point.
- Same `eks-restricted` `NetworkPolicy` overlay, TLS on, monitoring on, exactly as `eks-badfaith-sanity-2026-11-22`.
- **Calibrate the generator first**, at the largest planned size only, before trusting any broker-side number: holding up to ~1600 concurrent TCP+TLS+WebSocket sessions client-side is a real memory and file-descriptor cost to the generator pod itself (currently 2 CPU / 1Gi, `deploy/loadgen/overlays/eks/kustomization.yaml`), not just the broker. Watch `generatorSchedulingDelayP99Ms` and the generator's own cgroup CPU/throttling (both already reported) at that size before believing a flat or improving broker-side number; raise `generator_resources` (memory in particular, not yet pushed this high in any run so far) if it throttles or OOMs.

**What is *not* built yet, and needs its own look:** reading the broker's own connection/memory state. `cpuprobe` reports cgroup **CPU only** (confirmed by reading `components/cpuprobe/cgroup.go`) — no memory, no connection count. `nats-server`'s monitoring HTTP port is already enabled (`http: 0.0.0.0:8222` in `deploy/stack/base/broker-config.yaml`) but nothing in this benchmark reads it. Its `/varz` endpoint (unauthenticated, a plain `GET`) reports `mem` (RSS bytes) and connection-related counters natively, with no nats-server config change needed. Fetching it at the same burst-boundary points `probeCpu` already is (or, better, on a fixed interval through the whole 30s ramp window, since the question here is about a sustained level, not two snapshots) is new, small driver- or generator-side code, not yet written.

## Needs approval

Off by default, a new `--varz` flag turns it on. 20 new tests across `test_varz.py`, `test_jobs.py` and `test_ab.py`, all offline.
2. **Possibly raising the generator pod's memory** past 1Gi for the largest size point, found out during calibration, before the largest size is trusted. **Resolved, 2026-11-22: not needed.** The calibration run (see Outcome) found the generator fine as configured at size 6000 with the planned ramp (`generatorSchedulingDelayP99Ms` ~2ms, 0% throttled) — the 2 CPU/1Gi pod handles the ramped design without raising anything.
3. **Running the sweep on EKS** — ordinary EKS time (~$1.1/h, same cluster), one exploratory pass (1 block per size). **Size 6000 only, done 2026-11-22** as a side effect of the calibration run (see Outcome) — sizes 250, 1000 and 3000 have not run. Read the one size that exists as a lead, not a result ("few blocks mean nothing" applies doubly to one size out of four).

## Outcome

**2026-11-22, calibration run** ([eks-exhaustion-calibration-2026-11-22](../results/cfedersp/eks-exhaustion-calibration-2026-11-22/NOTES.md), full detail there). This was meant only to answer Design's calibration question (is the generator the limit at size 6000?) but, since that requires actually running size 6000 with the real fractions and ramp, it produced real data at the sweep's largest point too.

**Calibration: passes.** `generatorSchedulingDelayP99Ms` ~2ms, 0% cgroup CPU throttling, flat across all 8 reps of `main_exhaustion`'s ramped burst. The generator is not the limit at this size with `STORM_RAMP_MS=30000`; no change to `generator_resources` is needed before the rest of the sweep. (A side finding, not part of the calibration question: `main`'s own *unramped* burst at the same size 6000 throttles the generator 52-58% of periods — a new ceiling no earlier run at 800/1600 had reason to find, since it never ran this large unramped. Irrelevant to this plan's design, which always ramps, but worth knowing before anyone runs an unramped comparison at this size.)

**Correction to the Hypothesis:** `max_connections` (read from the broker's own `/varz`, now confirmed working — see below) is **65536**, not unconfigured/unlimited as the Hypothesis assumed from `broker-config.yaml` having no explicit setting. This is `nats-server`'s own default when the setting is absent. Still far above anything this sweep plans to reach, so it does not change any prediction, but "no `max_connections` configured" should read "defaults to 65536" — the Hypothesis itself is left as written, per this project's rule against editing it after the fact.

**Prediction 1 (held count tracks arrival rate × 10s): holds, within the stated factor of 2.** Peak concurrently-held connections, read from the `varz` poll's time series (not a two-snapshot bracket), reached **1999** against a naive estimate of 1600 for this size/fraction/ramp (4800 bad-faith connections over 30s = 160/s × 10s). The series resolution is the poll interval (~2.6s observed vs. 2s configured), so the true peak could be a little higher than what was sampled.

**Prediction 2 (good-faith degrades only once held count is large): not falsified, but not a strong confirmation either.** All 1200 good-faith connections per rep were admitted every time, zero refused/timeout/error, at a peak of ~2000 held. That is this plan's *largest* planned point, with no degradation at all — either the broker comfortably handles this volume (plausible: nats-server is built for far more connections than 2000), or 2000 is still not where any real bend is, and the smaller sizes (250/1000/3000, not yet run) would not add information in the direction this plan was looking (they predict *less* load, not more). If a bend exists, this sweep's whole planned range may be too low to find it — worth considering a size *above* 6000 before assuming the broker has no such limit at all.

**Prediction 3 (broker memory climbs, stays under 4Gi): the first half confirmed, the second half untested at anything near its edge.** Memory climbed from ~26MB to ~395MB across the 8 repeated bursts within the one Job — about 10% of the 4Gi limit, and notably **not fully recovering between bursts** (each burst's trough was higher than the previous one's: 117 → 211 → 199 → … → 341MB). Whether that is a genuine per-held-connection cost accumulating, or ordinary Go-runtime memory retention (RSS not returned to the OS after GC, common and not itself a problem), was not determined — a longer run (more reps, or a dedicated memory-over-time check with no bad faith at all as a control) would tell them apart, and matters more than finishing the ratio sweep as originally scoped.

**Falsifier 2 (forged/incompleteHandshake timing drifts under load): not triggered.** Both stayed tightly clustered at 10000-10007ms, even tighter than the 20-at-a-time sanity run's 10020-10047ms band — no sign of the broker's own timeout handling degrading at ~2000 concurrently held.

**`/varz` reading: fully confirmed against a real broker.** `mem`, `connections`, `total_connections`, `cpu` and `max_connections` all came back populated and sensible; the "not fully verbatim" caveat in `varz.py`'s docstring and `README.md` no longer applies and can be removed next time either file is touched.

**Next:** given Prediction 2's ambiguity (no evidence of a bend, but also no evidence the sweep's range is high enough to find one) and the more interesting open question being the memory-recovery pattern rather than the ratio itself, running the three smaller sizes (250/1000/3000) as originally planned is lower priority than either (a) a dedicated memory-over-time check to settle whether the non-recovery is real, or (b) trying a size well above 6000 to see if a bend exists at all. Neither is decided; this needs a conversation with the user before spending more EKS time in either direction.

**2026-11-22, memory-over-time follow-up** ([eks-exhaustion-memory-probe-2026-11-22](../results/cfedersp/eks-exhaustion-memory-probe-2026-11-22/NOTES.md), full detail there; not a `bench run` — `STORM_RUNS` is reserved by the plan's phases, so a one-off script called `KubeBackend.run_storm` directly to get 40 reps instead of 8). Settles Prediction 3's open half, and changes what this whole plan is actually about.

**Memory does not plateau: it climbs monotonically with cumulative connections, for the full 24-minute, 40-rep window** — 16MB to 1301MB, no sign of leveling off. That rules out ordinary Go-runtime RSS retention (which would stabilize once the peak live working set is reached) in favor of a real accumulating cost.

**This is not a bad-faith finding at all.** The calibration run's own `main` unit (pure good faith, no bad-faith settings, unramped) showed the identical pattern over its own short window: 37MB→1381MB over 48,641 connections, all admitted. Normalizing both runs by *admitted* connections (bad-faith connections are never admitted, so should not be expected to cost the same as a real one) gives 28.0 KB/admitted-connection for `main` and 26.8 KB/admitted-connection for this run — two runs that share almost nothing else (different ramp, different bad-faith fraction, 22x different duration) landing within 5% of each other. **Something in the connection-admission path appears to retain roughly 27KB per admitted connection, indefinitely** — a risk for any sustained high-churn workload against this broker configuration, attack traffic or not. This plan was built to answer a bad-faith-specific question (`plans/bad-faith-storm.md`'s `forged`/`incompleteHandshake` kinds); it has instead found something that looks broader and more fundamental, and not yet explained — the attribution to "connection admission" is inferred from two runs agreeing, not traced in source or profiled (this benchmark harvests CPU/block/mutex profiles but not heap profiles; a `pprof` heap snapshot at two points in a long admitted-only run is the natural next step if this is pursued, and would show what is actually growing rather than just that something is).

**This likely deserves its own plan going forward** (a connection-churn memory-growth question, not a bad-faith-exhaustion one), rather than continuing to treat it as a finding of `held-connection-exhaustion`. Split into `plans/admitted-connection-memory-growth.md` (also dropped for now, see its own Outcome).

**2026-11-22: dropped.** Satisfied with the broker's performance and confident the implementation is sound on the strength of what this plan already found (the calibration passing, no good-faith degradation at the tested range, the memory-growth lead now split out). The ratio sweep's other three sizes were never run and are not planned now; revisit when there is a reason to scale.
