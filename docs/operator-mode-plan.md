Findings from step 1 that change the plan:

- **A refused ticket can take the broker's authorization timeout.** A ticket that fails the scoped-signer check (permissions of its own) is handed to the callout of an account that has none, and the server waits for an answer that never comes, so the client sees a timeout after the default 2s instead of an immediate error. A refusal from the callout itself is immediate, and so are an unknown operator and no credentials. The generator should treat a slow refusal as a result, not retry it, and its connection timeout must be longer than the broker's authorization timeout.
- **nats-server joins every `include` path to the including file's directory, even an absolute one.** `include "/etc/storm/operator/operator.conf"` would have failed in the pod (it looks under `/etc/nats/etc/storm/...`). The broker config includes `../storm/operator/operator.conf`, which resolves to the mount from `/etc/nats`. A test boots the rendered config to keep this honest, and checks the include path against `provision`'s `DefaultMountDir`.
- **`max_control_line: 16384` is needed for long tickets.** With the default (4096), a ticket with 70 role tags is refused with "maximum control line exceeded"; with the setting it connects. A normal ticket with a few tags fits in the default.
- **The refusal delay now equals the generator's default timeout.** `authorization.timeout` is 10s and `STORM_TIMEOUT_MS` defaults to 10000, so a ticket that is refused only after the broker's timeout and the generator's own give-up race. The generator's default timeout should be longer (step 4).
- **A pod's volumes are set up before its init containers run.** A Secret volume for an object the init container creates would keep the callout pod from starting, so the callout reads its keys through `secretKeyRef` environment variables, which are resolved when its container starts. The broker and generator pods are separate pods, so they can wait for their objects (the broker mounts the ConfigMap; kubelet retries a missing mount with growing intervals, so they may start late).
- **The role-name mapper in the benchmark is a generic re-implementation, not a copy.** `oidc-auth-callout`'s mapper implements a private naming convention with sensor, form-session and realm-role-table families; the public benchmark has only the application-feed family (`app-feed-publish-*` / `app-feed-subscribe-*`) and no wildcard grants. Say if more should be copied.
- **The `Connz` monitoring endpoint reports a connection's account only when asked for auth detail** (`auth=1`); worth remembering for any check of which account a connection landed in.

## Goal

**Replace** the benchmark's current authentication (config mode with a password callout) with **operator mode with an auth callout**. Config mode is removed, not kept as an option. The point is to let the framework compare broker builds and configurations under the authentication path a deployment with an operator and accounts would use, without bringing in the services such a deployment has around it (an identity provider, a signing service, a share coordinator).

## Today (config mode), removed by this plan

- The broker config declares `accounts { SYS, AUTH, A0..A15 }` and `authorization { auth_callout { issuer, account: AUTH, auth_users: [auth] } }`. There is no operator.
- The callout (`components/callout`) takes a username `u<N>` and one shared password, and answers with a user JWT in account `A<N>`, signed with an issuer seed from the Secret `storm-secrets`.
- The generator (`components/loadgen`, a hand-written WebSocket client) sends `user` and `pass` in CONNECT (`STORM_AUTH=plain`, or `none` with no credentials).
- `bench secrets create` runs `callout keygen` in the callout image and stores `storm-secrets` and `storm-tls`.
- Leaf nodes authenticate with `LEAF_PASSWORD` in the broker config.

What goes away: the password path in the callout, `callout keygen`, `CALLOUT_ISSUER_SEED` / `CALLOUT_USER_PASSWORD` / `CALLOUT_SERVICE_PASSWORD`, `STORM_AUTH`, `STORM_ACCOUNTS` and the `A0..A15` accounts, the `storm-secrets` Secret, and the leaf-node component (see decisions 5 and 7).

## Target (operator mode)

### Trust chain

| Item | Made by | Stored as | Held by |
|---|---|---|---|
| Operator JWT (operator signing key is discarded after signing, see below) | provision init container | ConfigMap | broker config |
| SYS account JWT | provision init container | ConfigMap | broker |
| AUTH account JWT (auth callout enabled, `allowed_accounts`, the callout's user key as an auth user, and the scoped signing key with a zero-permission template) | provision init container | ConfigMap | broker |
| Scoped AUTH signing key (seed) | provision init container | Secret | **generator only** |
| Tenant account JWT (a single tenant account) | provision init container | ConfigMap | broker |
| Tenant account signing key (seed, not scoped); signs the user JWT the callout mints | provision init container | Secret | **callout only** |
| AUTH account signing key (seed, not scoped); signs the callout's response claim | provision init container | Secret | **callout only** |
| Callout's own login (user JWT and seed, in AUTH) | provision init container | Secret | callout |

The AUTH account JWT must also list the tenant account in its callout `allowed_accounts`, and the minted user JWT carries `issuer_account` = the tenant account's public key (it is signed by a signing key). I read the server's checks in `server/auth_callout.go` (lines ~150-215): in operator mode the **response** claim must be signed by the AUTH account or one of its signing keys, and the user JWT inside is placed in the account named by its issuer or `issuer_account`, which must be allowed. An earlier draft of this plan left out the AUTH response signing key; the table above has it now. The scoped AUTH key cannot be used for this, since a scoped key only signs empty-permission user JWTs, so the callout holds a second, plain AUTH signing key.

The broker never holds a seed. The generator never holds the tenant signing key, so it cannot mint a user with permissions. JWTs are public and go in a ConfigMap; seeds go in Secrets.

The operator and account identity seeds are only needed to sign the JWTs, so the init container signs everything in one run and then discards them (the same approach `secretgen.py` takes with the throwaway TLS CA). Only the seeds in the "Held by" column above survive. This means accounts cannot be edited later without re-provisioning, which is acceptable for a throwaway lab.

### Per-connection flow

1. The generator opens the WebSocket and reads INFO, including the nonce.
2. It builds a user JWT and signs it with the scoped AUTH key. The JWT has an empty permission set (the scoped key's template supplies zero permissions), a fresh user nkey as subject, an `exp` one hour after signing, and the requested role names as tags. It signs the nonce with the user key and sends CONNECT with `jwt` and `sig`.
3. The broker finds the user in AUTH, sees the callout enabled in the AUTH account JWT, and sends a request to the callout.
4. The callout validates the request's user JWT, maps the tags to subjects with the role-name mapper, and replies with a response claim (signed with the plain AUTH signing key) carrying a user JWT for the tenant account, signed with the tenant signing key, with `issuer_account` set to the tenant account and `exp` one hour after minting.
5. The broker admits the connection into that tenant account.

This is the private stack's zero-permission flow without the identity provider and the signing services.

### Provisioning: an isolated init container

A separate program, `components/provision` (its own image, built with the Go `nats-io/jwt/v2` and `nkeys` libraries, no `nsc` binary), runs as an **init container of the callout pod** and writes the Secrets and ConfigMap through the Kubernetes API. The callout binary does not carry any provisioning code: the callout image stays the trimmed responder.

- **Idempotent.** If the named objects already exist it exits without doing anything. The driver restarts the callout at every variant start, so keys stay the same across variants and blocks. To get new keys, delete the objects (`bench secrets delete` is extended to cover them) and restart the pods.
- **Narrow permissions.** A dedicated ServiceAccount with a Role in `storm-bench` allowing `create` (and `get`, for the existence check) on only the named Secrets and ConfigMap, no `update`, `patch`, `list` or `delete`.
- **Token only in the init container.** Set `automountServiceAccountToken: false` on the pod and mount an explicit projected ServiceAccount token volume in the init container only, so the callout container does not hold a credential that can write Secrets. This is expected to work but has not been tried here (see risks).
- **Creation race.** Only the init container creates these objects. If a second writer ever appeared, `create` failing with "already exists" must be treated as success after a re-read, not as an error.
- **Start order.** The broker and generator mount objects the init container creates. A pod that mounts a missing Secret waits in `ContainerCreating` until it exists. The driver's rollout wait must be checked against this (risks).
- **Outside the kustomization.** The objects are made by the pod, not by the kustomization, so they are not part of the "same Kubernetes objects in every variant" check in preflight, and `kubectl apply -k` without `--prune` (what the driver does) does not delete them. With config mode removed, every pod mounts them unconditionally (no `optional: true`).
- **`bench secrets create` shrinks.** With the passwords, `keygen` and the issuer seed gone, it makes only `storm-tls` (the throwaway TLS CA and certificate), and no longer needs a container tool to run a keygen image. Preflight's Secret check becomes a check for `storm-tls`; it cannot check for the init container's objects before the stack is up (see risks).

### Callout: trimmed from `oidc-auth-callout`

Keep: request decode, the role-name mapper, mint and sign, the response wrapper, the callout's own connection by credentials.
Drop: JWKS and token verification, sealing and curve keys, proof of possession, the connection-key mapper, share grants, the stateful enricher. Also removed from the benchmark callout: the password path, `keygen`, and the `u<N>` username scheme.

**Expiry.** The minted user JWT carries `exp` = mint time + 1 hour (a setting, default 1h; the jwt library sets `iat` itself and the benchmark callout sets no `exp` today). In `oidc-auth-callout` the `exp` is copied from the OIDC token; there is no token here, so the callout sets it from the configured lifetime. `nbf` stays unset. The broker disconnects a client whose JWT has expired, so a connection held past an hour is closed by the server; the benchmark's connections are short-lived (a burst, then closed), but see the risks.

The role-name mapper in `oidc-auth-callout` reads `realm_access.roles` and client roles from verified OIDC claims. In the benchmark there is no token, so the callout builds the same claim shape from the tags on the user JWT. The generator signs those tags itself, so roles are self-asserted. That is acceptable for a load tool and must be stated in the README.

Because it does less per connection than the real callout, results in this mode say nothing about the real callout's cost. They characterize the broker and the callout round trip.

### Generator

- Operator mode is the only mode: `STORM_AUTH` (`plain` / `none`) and `STORM_ACCOUNTS` are removed, and the generator reads the scoped signing key from its Secret instead of `STORM_PASSWORD_FILE`.
- Keep the hand-written client. A check of `async-nats` 0.53.0 (source read only, nothing compiled) found it can expose the CONNECT-sent and answer timings through the nonce-signing callback and the return of `connect()`, but not the WebSocket-open timing (used only in per-connection samples). It adds two tasks and a ping timer per connection and a different CONNECT body, so the timings would differ from the hand-written client's. It also does not build JWTs, so the encoder is needed either way.
- A small nkey and user-JWT implementation (header, claims, base64url, signature by the scoped key) on `ring` and `data-encoding`, not the `nkeys` crate (see Status, step 4).
- **Pre-sign the zero-permission user JWTs** (and generate their user keys) before the timed burst. The benchmark measures the broker and the auth callout, not the generator's JWT signing, so that cost stays out of the measurement. This is fixed behaviour, not a setting.
- **The nonce signature cannot be pre-signed.** The nonce comes in each connection's INFO, so the generator signs it with that connection's user key after INFO arrives. In `auth-storm` today the "auth" interval starts when CONNECT is written (`sent_at`) and the nonce is signed before that, so the signature is outside "auth" but inside "total" (start to PONG). Report this in the README: "total" in operator mode includes one ed25519 signature per connection on the generator's side, and "auth" does not.
- Give the generator's JWT an `exp` of one hour after signing, the same lifetime as the minted one (a setting). Pre-signed tickets are made before each burst, outside the timed interval, so a ticket is never an hour old when used; if signing once at generator start turns out to leave tickets older than that, sign before each burst instead.

## Work breakdown

Do these in order. Steps 1-4 add the operator-mode path next to the existing one, so the existing tests keep passing while it is built; step 6 deletes config mode, so the end state has one mode. As built, step 3's callout reads only Secrets through environment variables (it never reads the ConfigMap), and the steps' interim pieces (the operator component, `local-operator`, `--mode`, the preflight `auth` check) were removed in step 6; see Status.

1. **Provision program** (new `components/provision`, own image): builds the operator, SYS, AUTH and tenant accounts, the scoped and plain signing keys and the callout's user; signs everything; discards the identity seeds; writes the Secrets and ConfigMap (create-only, skip if present). Tests: decode every JWT with the library's own validators, including `UserScope.ValidateScopedSigner` against a JWT shaped like the generator's; a fake Kubernetes client test for the idempotent skip and for "already exists" handling. Add the ServiceAccount, Role and RoleBinding manifests.
2. **Broker config** (`deploy/stack/base/broker-config.yaml` and overlays): the operator-mode config with `operator` (path into the mounted ConfigMap), `system_account`, and the MEMORY resolver with its preload. Keep the resolver in its own `include`d fragment, written by the init container into the ConfigMap, rather than spread through the base config, so a later resolver choice replaces one fragment (see "Later versions"). Include `max_control_line` as the private stack does (16384), since operator-mode CONNECT lines carry a JWT.
3. **Trimmed callout** (`components/callout`): an operator-mode path next to the password path, selected by environment, reading its seeds from the Secrets the init container made (mounted into the callout container) and the tenant account JWTs from the ConfigMap. The init container is added to the callout pod spec in an operator-mode overlay/patch with `automountServiceAccountToken: false` and the explicit token mount. Unit tests per stage; an e2e test with an in-process server like the existing `e2e_test.go`.
4. **Generator** (`components/loadgen`): operator mode, encoder, tests. A cross-check that decodes the Rust encoder's output with the Go validators, since a one-byte difference makes the server refuse every connection.

## Risks and unverified items

- **Scoped-key template.** In NATS an empty allow list means unrestricted. The zero-permission template on the scoped key must carry explicit denies, and this must be checked against a running server. The private repo's script flags its own `nsc edit signing-key --role` step as unverified against a live `nsc`. Treat the library's `HasEmptyPermissions` check as a precondition, not proof the template restricts anything.
- **Scoped-signed JWT shape.** `ValidateScopedSigner` (jwt/v2 v2.8.2) requires the issuer to be the scoped key and `UserPermissionLimits` to be empty. `NewUserClaims` defaults `NatsLimits` to -1, which fails the empty check, so the generator's encoder must omit limits. Tags, name and issuer account are allowed.
- **Token isolation.** That a projected ServiceAccount token volume mounted in the init container only, with automount off for the pod, keeps the token out of the other containers is expected from Kubernetes' behaviour but has not been verified on the kind or EKS versions used here. Verify it (try to read the token path from the callout container).
- **Pod start order.** Whether the broker pods' wait for the objects interacts badly with the driver's rollout timeout, and whether a mounted Secret or ConfigMap that appears late is picked up without a restart, has not been checked.
- **Rollout restarts the callout and so re-runs the init container.** Idempotence must hold under that; a bug that regenerated keys on a restart would split the broker's trusted JWTs from the callout's seeds.
- **Cluster behaviour.** Account JWTs in a MEMORY resolver preload are the same on every broker; whether anything else about operator mode differs in a cluster has not been tested here.
- **One tenant account** puts every connection in the same account, where config mode spread them over 16. Per-account state in the server is then shared by all connections, so operator-mode results are not comparable to the earlier config-mode ones on this dimension either.
- **Expiry.** A connection kept longer than an hour is disconnected by the server when its JWT expires. Check that nothing in the benchmark (a long idle phase, a held connection, a long-lived generator Job) can reach an hour; the 1 hour setting is meant to be raised if needed.
- **Fixed cost per connection** changes: a larger CONNECT, a JWT validation and a different callout request. Do not compare new results to the earlier config-mode numbers as if only the broker changed. Because config mode is removed, there is no way to re-run the old configuration from the new code; to compare, check out the earlier commit.
- **Broker pods now depend on the init container.** Every broker pod mounts objects the callout pod's init container creates, with no `optional: true` fallback. If the callout pod fails to start (a bad image tag, a missing ServiceAccount), the broker pods sit in `ContainerCreating` and the run looks like a broker problem. Preflight should name the callout image and the ServiceAccount, and the rollout wait should report which pod is waiting on what.
- **Generator load.** Pre-signing moves the JWT cost out of the timed interval but holds every ticket and user key in memory during the burst; at 1600 connections this is small, but confirm. The per-connection nonce signature still runs on the generator inside each burst, and the generator's reported scheduling delay is how a limit there would show up.

## Later versions (not the first draft)

The tester will be able to choose two things that the first draft fixes. The first draft should not make them hard to add, but should not build them either.

- **Resolver:** MEMORY (first draft), and later the full resolver (a writable directory per broker pod, accounts pushed or seeded) and possibly the cache resolver. The hook is the separate resolver config fragment above. The init container should write the JWTs as plain files in the ConfigMap (operator, SYS, AUTH, tenant) as well as the MEMORY fragment that embeds them, so another resolver's fragment can be built from the same files. Not designed here: how the full resolver's directory is seeded in each pod, and what `nsc push` would need.
- **Leaf nodes:** none in the first draft. A later version brings back the leaf component with leaf credentials inside an account and lets the tester pick whether to run it, as the `leafnodes` kustomize component is chosen today. Not designed here: which account the leaf user lives in, or how a leaf connection authenticates in operator mode.

These would be selected the way the repository selects cluster shape today (a kustomize component per choice, named in a variant), but that mechanism is not designed here either.

## Out of scope

Identity provider integration, sealing and proof of possession, share grants, the stateful enricher, leaf nodes and a choice of resolver (both for later versions, above), signing services, a config-mode or no-auth option.
